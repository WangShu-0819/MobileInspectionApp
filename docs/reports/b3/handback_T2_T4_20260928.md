## T4：ROI 相似度兜底

### 源码审查与实现

审查确认原 Android 确认流程有 NanoDet 单独结果和人工改判证据，但没有 NanoDet NG 后的 ROI 相似度链路。现实现放在生产确认流程中：每个实际 NanoDet NG 的 ROI 先保存裁剪图，再运行 AKAZE 配准；仅配准通过后，把现场 ROI 对齐到模板 ROI 并计算灰度 SSIM。人工确认仍单独保存，不由相似度候选自动改写。

- 所有 NanoDet 支持的部件类别都走相同的 NG 触发链路：exp09 的 NUT/THREAD/BOLT/NUTSERT，exp22 黑件的 THREAD/NUTSERT/NUT/BOLT，以及 exp23 白件的 NUT/THREAD。白件 BOLT/NUTSERT 按既有模型协议标为 `MODEL_TARGET_UNSUPPORTED`，不会伪装成 NG，也不会触发 NG 兜底。
- 每个实际相似度调用开始前，先把 ROI 图片写入应用的 ROI evidence 存储；比较失败或配准拒绝时仍保留图片并记录状态。图片不可用或保存失败时不调用比较，写入 `ROI_IMAGE_UNAVAILABLE` 或 `ROI_EVIDENCE_SAVE_FAILED`，分数、阈值和候选均为空。
- 表格分别写入 NanoDet 状态/结果、相似度状态/分数/阈值/候选、人工最终结果、`humanChangedModel`、原改判 ROI ZIP 路径和相似度 ROI ZIP 路径/状态。相似度图片在检查 ZIP 中单独归档；CSV 路径与 ZIP entry 对应。
- 错误状态明确区分模板/照片不可读、OpenCV 运行库不可用、ROI 无效、配准失败、比较错误、证据图不可用/保存失败。NanoDet 推理错误与模型不可用继续写 NanoDet 状态；没有实际 NanoDet NG 时相似度为 `NOT_RUN_NANODET_NOT_NG`，不生成 OK/NG 候选。
- `0.95` 只用于 `Black_` 部件的 THREAD ROI，且仅是 Black Thread 人工监督试点候选；其他类别只记相似度分数，不提供阈值或 OK/NG 候选。`0.75` 不是相似度阈值；既有离线报告中的 `0.75` 是 Lowe 特征匹配比率。

### 类别、预处理、shape、decoder 与坐标还原

- exp22 类别顺序为 `Black Thread, Black Nutsert, Black Nut, Black Bolt`，应用映射 THREAD→0、NUTSERT→1、NUT→2、BOLT→3。exp23 为 `White Nut, White Thread`，映射 NUT→0、THREAD→1；白件 BOLT/NUTSERT 明确不支持。
- 两个配置输入均为 416×416、`keep_ratio=true`。生产 Android 前处理为 BGR、OpenCV `INTER_LINEAR` 等比缩放/左上对齐、mean `[103.53,116.28,123.675]`、std `[57.375,57.12,58.395]`，归一化后补零。导出日志分别显示 PyTorch 输出 `(1,3598,36)` 和 `(1,3598,34)`。
- `reg_max=7`，decoder 每个点读取类别分数和四边各 8 个 DFL bin；候选分数门槛 0.05，按类别 NMS IoU 0.6；业务 OK 门槛仍为 0.50。框坐标用实际 `scaleX/scaleY` 还原到原始直立 ROI/照片范围。
- 生产 JNI 检查实际 NCNN `Mat.dims=2`、`w=outputWidth`、`h=3598`、float32 后才展开输出。exp22 生产推理输出 129,528 个元素；exp23 输出 122,332 个元素。真图运行的辅助 Mat 元数据探针读得 exp22 `[dims=2,w=36,h=3598,elemsize=4]`、exp23 `[2,34,3598,4]`，明确确认 exp23 的 `Mat.w=34`。

### 真图 parity

最终连接设备测试使用真实图像 `frame_00000_f0.jpg`（720×1280，EXIF 1，SHA-256 `f9fcc75a2f4047db35fcd2b884e1bdf5bab3ce7addce8610c40a99469942ded6`）以及桌面参考张量。Android 实际图像解码/方向处理→生产 `NanoDetImagePreprocessor`→`NanoDetNcnnNative`→`NanoDetOutputDecoder` 与桌面参考比较。当前生产 runtime 文件 `libnanodet_ncnn_runtime.so` SHA-256 为 `218AFA3655CC853D9CBF2A2D05BD65B43EFA72AC0314DAC2D28D2385193BEF32`。

当前运行的 JUnit XML 为 2/0/0/0（exp22、exp23 均通过）。本轮 logcat JSON 中，Android 与桌面的输入 tensor SHA 完全一致；生产 runtime 输出与桌面输出 max abs diff 分别为 exp22 `3.3080578e-6`、exp23 `3.2186508e-6`，均小于 `1e-5`。两模型各有 3 个 NMS survivor，类别/保留项相同；最大分数差分别 `6.5565109e-7` / `5.9604645e-8`，最大框坐标差分别 `1.5758757e-5` / `1.4480915e-5` 像素，均在记录容差内，坐标均在图像范围内。

实际推理调用的是生产 `libnanodet_ncnn_runtime.so`。测试专用 `libncnn_smoke.so` 只额外暴露真实输出 Mat 的 `w/h` 元数据；其 tensor 与生产 JNI 输出逐元素比较 max diff 为 0，作为 shape 读数辅助，不替代生产 runtime 推理。此 parity 与 T4 ROI 相似度计算无关。
